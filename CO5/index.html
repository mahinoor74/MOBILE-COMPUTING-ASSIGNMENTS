A1 - Constraint-Aware Intent & Service Architecture

7 Marks

Problem Model

Input: Sensor events, network state, battery level, user preferences and permissions.

Output: Uploaded records and critical-event notifications.

Decision: Collect, upload, defer, retry, notify or cancel.

Constraints: Battery, Doze mode, permission, encryption and connectivity.

Goal: Upload valid data securely while maintaining application responsiveness.

Runtime State

  • Pending work ID and record ID.
  • Task status: queued, running, deferred or completed.
  • Retry count and next execution time.
  • Permission and authentication status.
  • Battery and network state.
  • Encryption and upload checkpoint status.

Feasibility Conditions

Execute: Permission is granted, data is encrypted and constraints are satisfied.

Defer: Network is unavailable, battery is low or Doze blocks non-critical work.

Reject: Data is invalid, unencrypted or unauthorised.

Cancel: User logs out or withdraws permission.

Architectural Pseudocode

PROCEDURE SCHEDULE_HEALTH_WORK(state)

WHILE pendingQueue is not empty

    work = SELECT_NEXT_WORK()

    candidate = CREATE_EXPLICIT_INTENT(work)

    IF permission is denied
        REJECT(work)
        CONTINUE
    END IF

    IF user is not authenticated
        CANCEL(work)
        CONTINUE
    END IF

    IF data is not encrypted
        ENCRYPT_AND_VALIDATE(work)
    END IF

    IF encryption fails
        REJECT(work)
        CONTINUE
    END IF

    IF device is in DOZE AND work is not critical
        DEFER(work)
        CONTINUE
    END IF

    IF network is unavailable OR battery is low
        DEFER(work)
        CONTINUE
    END IF

    ENQUEUE_UNIQUE_WORK(candidate)

    result = EXECUTE(work)

    IF result = SUCCESS
        MARK_COMPLETED(work)
        UPDATE_CHECKPOINT(work)

    ELSE IF result = RETRYABLE_FAILURE
        SAVE_CHECKPOINT(work)
        SCHEDULE_RETRY(work)

    ELSE
        ROLLBACK(work)
        CANCEL(work)
    END IF

END WHILE

RETURN FINAL_STATUS

END PROCEDURE

A2 - Safe Data Synchronisation

5 Marks

Problems with Naive Synchronisation

  • Uploads every record without checking priority.
  • Repeated network failures waste battery.
  • Large files consume unnecessary bandwidth.
  • Conflicting records are not identified.
  • Sensitive data may be exposed without encryption.

Incremental Synchronisation Pseudocode

PROCEDURE SAFE_SYNC(records, environment)

syncSet = EMPTY

FOR EACH record IN records

    IF record is deleted
        DISCARD_OR_SEND_TOMBSTONE(record)
        CONTINUE
    END IF

    IF record is not encrypted
        REJECT(record)
        CONTINUE
    END IF

    IF record has version conflict
        RESOLVE_CONFLICT(record)
        CONTINUE
    END IF

    IF network quality is insufficient
        DEFER(record)
        CONTINUE
    END IF

    IF battery is low AND record is not critical
        DEFER(record)
        CONTINUE
    END IF

    ADD record TO syncSet

END FOR

UPLOAD(syncSet)

END PROCEDURE

R3 is rejected before upload because its contents are not encrypted. Uploading it would violate the security condition.

Offline-First Challenge

Under eventual consistency, temporarily unavailable records must be preserved locally. Permanent deletion because of poor connectivity is no longer valid. The system should use retries, durable storage and conflict resolution.

Generic Background Framework

PROCEDURE SCHEDULE_OR_EXECUTE(state)

    UPDATE_ENVIRONMENT(state)

    work = SELECT_NEXT_CANDIDATE(state.queue)

    IF work does not exist
        RETURN IDLE
    END IF

    IF NOT AUTHORIZED(work)
        REJECT_AND_CLEANUP(work)
        RETURN
    END IF

    IF NOT FEASIBLE(work)
        DEFER_WITH_CHECKPOINT(work)
        RETURN
    END IF

    SAVE_PREVIOUS_STATE(work)

    result = EXECUTE(work)

    IF result = SUCCESS
        COMMIT(work)

    ELSE IF result = RETRYABLE
        RESTORE_CHECKPOINT(work)
        SCHEDULE_RETRY(work)

    ELSE
        ROLLBACK(work)
        RELEASE_RESOURCES(work)
    END IF

END PROCEDURE

Role of Undo and Cancellation

Undo restores the previous valid state after a failure. For example, if an upload is cancelled halfway, the application should remove incomplete temporary data and preserve the original local record. Otherwise, data corruption or duplication may occur.

Inquiry

Performance is not only about speed. It also includes latency, memory, battery usage, network traffic, reliability and frame deadlines.

Local processing improves offline availability and can protect privacy, but consumes device resources. Cloud processing provides greater computing capacity but depends on connectivity, introduces network latency and requires secure data transfer.

A5 - UI Performance and Approximation

4 Marks

Exact Optimisation

Exact search examines every combination of decoding quality, cache size and prefetch distance. It selects the configuration with the lowest cost while satisfying the frame-time target.

As the number of feed items, device types and configuration levels increases, the search space grows rapidly.

Adaptive Heuristic Pseudocode

INITIALISE quality, cacheSize, prefetchWindow

REPEAT

    metrics = MEASURE(frameTime, battery, memory)

    IF frameTime > 16 OR memory is HIGH
        REDUCE quality
        EVICT old cache items
        REDUCE prefetchWindow

    ELSE IF frameTime < 12 AND battery > 40
        INCREASE quality carefully
        INCREASE prefetchWindow
    END IF

    APPLY_PARAMETERS()
    UPDATE_STATE()

UNTIL parameters remain stable

RETURN selected configuration

What Is Sacrificed?

A heuristic can quickly find a feasible smooth-scrolling configuration. However, it does not prove that the selected parameters minimise total energy. It may find a local solution instead of the global optimum.

Production Engineering Decision

Exhaustive search is expensive when thousands of devices and many encoding combinations are involved. A practical heuristic quickly selects a feasible resolution and bitrate based on device capability, battery and network speed.

The heuristic does not guarantee global optimality. Engineers should monitor upload completion, energy usage, thermal throttling, video quality and failure rate before production deployment.
